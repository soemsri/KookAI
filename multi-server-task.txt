[x] Phase 1: Data Storage & API Refactoring (โครงสร้างข้อมูลและการจัดเก็บ)
    ---------------------------------------------------------------------------
    [x] Task 1.1: อัปเดตและนิยาม Data Types & Interfaces ใน `mobile/utils/api.ts`
        - [x] กำหนด interface `ServerNode`:
              - `id`: string (Unique UUID หรือ hostId)
              - `name`: string (ชื่อเรียก Server เช่น "Office PC", "Home Mac")
              - `hostId`: string (Host ID จาก Broker)
              - `url`: string (Cloudflare/WAN Public URL)
              - `localIp`: string (IP Address ใน LAN)
              - `port`: number (ค่าเริ่มต้น 8080)
              - `token`: string (JWT Auth Token ของ Server นั้น)
              - `createdAt`: number (Timestamp)
              - `lastActive`: number (Timestamp การใช้งานล่าสุด)
              - `connectionState`: 'local' | 'wan' | 'offline'
        - [x] กำหนด interface `MultiServerConfig`:
              - `activeServerId`: string | null
              - `servers`: Record<string, ServerNode>

    [x] Task 1.2: พัฒนาระบบ Data Migration จาก Single-Server เป็น Multi-Server
        - [x] เพิ่ม Key ใหม่ `kookai_multi_server_config` ใน SecureStore
        - [x] สร้างฟังก์ชัน `migrateLegacyConnection()` เพื่อตรวจสอบ Key เดิม (`kookai_server_url`, `kookai_local_ip`, `kookai_token`, `kookai_host_id`)
        - [x] หากพบข้อมูลเดิม ให้แปลงเป็น `ServerNode` (ตั้งชื่อเริ่มต้นว่า "Primary Host") แล้วบันทึกลง `MultiServerConfig` อัตโนมัติ พร้อมตั้งเป็น `activeServerId`
        - [x] ลบหรือทำเครื่องหมายข้อมูล Legacy หลังจาก Migration สำเร็จ

    [x] Task 1.3: พัฒนา Storage Helper APIs ใน `mobile/utils/api.ts`
        - [x] ฟังก์ชัน `getMultiServerConfig()`: ดึงข้อมูล Config ทั้งหมดจาก SecureStore
        - [x] ฟังก์ชัน `saveMultiServerConfig(config: MultiServerConfig)`: บันทึกข้อมูล Config ลง SecureStore
        - [x] ฟังก์ชัน `getSavedServers()`: คืนค่า Array ของ `ServerNode` ทั้งหมด
        - [x] ฟังก์ชัน `saveServer(server: ServerNode)`: เพิ่ม Server ใหม่ หรือ อัปเดต Server เดิม (เช็คจาก id/hostId)
        - [x] ฟังก์ชัน `removeServer(serverId: string)`: ลบ Server ออกจาก Config (หากเป็น activeServerId ให้สลับไปยัง Server ที่เหลืออยู่ หรือรีเซ็ตเป็น null)
        - [x] ฟังก์ชัน `setActiveServerId(serverId: string)`: อัปเดต Active Server ID และ `lastActive` timestamp
        - [x] ฟังก์ชัน `getActiveServer()`: คืนค่า `ServerNode` ที่เลือกใช้งานปัจจุบัน

[x] Phase 2: Dynamic Routing & Connection Health Check (การเชื่อมต่อและตรวจสถานะ)
    ---------------------------------------------------------------------------
    [x] Task 2.1: พัฒนาระบบ Per-Server Active URL Resolution
        - [x] ปรับปรุงฟังก์ชัน `getActiveBaseUrlForServer(server: ServerNode, forceRefresh?: boolean)` ให้ทดสอบการเชื่อมต่อเฉพาะ Server นั้นๆ
        - [x] ขั้นที่ 1 (LAN First): ทดสอบ `http://${server.localIp}:${server.port || 8080}` ด้วย timeout 2,000 ms
        - [x] ขั้นที่ 2 (WAN Second): ทดสอบ `server.url` ด้วย timeout 4,000 ms
        - [x] ขั้นที่ 3 (Broker Resolution): สอบถาม `WORKER_BASE_URL/resolve-host/${server.hostId}` หาก LAN/WAN เดิมติดต่อไม่ได้ เพื่อดึง URL/IP ล่าสุด
        - [x] อัปเดต `connectionState` ('local' | 'wan' | 'offline') ลงใน ServerNode และ Cache ผลลัพธ์

    [x] Task 2.2: พัฒนาระบบ Real-time Server Health & Ping Check
        - [x] สร้างฟังก์ชัน `pingServer(server: ServerNode)`: ส่งคำขอ `/api/health` หรือ `/` เพื่อวัด Response Time (ms) และสถานะออนไลน์
        - [x] สร้างฟังก์ชัน `pingAllServers()`: ตรวจสอบสถานะ Server ทั้งหมดใน Background เพื่ออัปเดต Badge สีบนหน้าจอ
        - [x] คืนค่าสถานะ:
              - 🟢 Local LAN (Latency ต่ำสุด)
              - 🟡 Public WAN / Cloudflare Tunnel
              - 🔴 Offline / Unreachable

    [x] Task 2.3: ปรับปรุง `apiCall()` ให้รองรับ Multi-Server Context
        - [x] ปรับแก้ `apiCall()` ให้ดึง Token และ Base URL ของ Active Server โดยอัตโนมัติ
        - [x] หากคำขอตอบกลับ 401 Unauthorized ให้แจ้งเตือน Token หมดอายุเฉพาะ Server นั้น
        - [x] หากเกิด Network Failure ให้ทำ Auto-Fallback Resolution เฉพาะ Active Server ก่อนแสดงข้อความสลับ Server
